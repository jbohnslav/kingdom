# Add sample input-output pairs to the kingdom skill

The kingdom skill (skills/kingdom/SKILL.md) needs to teach agents two things: **when** to reach for `kd` and **how** to invoke it correctly. Right now the skill describes capabilities and has a Quick-Ref with bare command names, but lacks the conversational instinct and flag knowledge agents need to get it right on the first try.

## What to add

### 1. Conversational triggers ("When to reach for `kd`")

A short section of worked examples showing agents how to recognize implicit cues in conversation and translate them into the right `kd` action. Each trigger should show the recognition moment, any clarifying questions the agent should ask, and the resulting command with realistic flags.

Triggers to cover:
- **User reports a bug** — extract actual/expected behavior, then open a ticket: `kd tk create -t bug -d "web app shows X, expected Y" "Backend rendering issue"`
- **User describes a problem conversationally** — e.g. "hey there's something wrong with the backend" → ask clarifying questions (what happened, what should happen, where, repro steps), then structure it into a ticket
- **User wants to track an idea** — suggest a backlog ticket: `kd tk create --backlog "title"`
- **User says work is done** — close the ticket: `kd tk close ab12`
- **User is stuck on a design choice** — ask council: `kd council ask "should we use X or Y for Z?"`
- **User says "ask the council"** — decide whether to continue an existing thread or start a new one. If the conversation is a continuation of an active design discussion, default to the current thread. If the topic has shifted materially or the old thread is resolved, start fresh with `--new-thread`. When ambiguous, check existing threads (`kd council list` / `kd council show <thread>`) or ask a brief clarifying question before running the command.
- **User wants to note progress** — log it: `kd tk log ab12 "finished the refactor, tests passing"`
- **User wants parallel execution** — start a peasant: `kd peasant start ab12`

At least one example should show the agent asking clarifying questions before creating the ticket (not just jumping straight to `kd tk create`).

### 2. Automatic worklog updates ("When to log without being asked")

Agents should proactively `kd tk log` whenever a durable state change occurs. The King should never have to say "update the worklog." Log against the active ticket without asking which ticket — the agent knows what it's working on.

The threshold is **durable state change**, not every chat turn. If future-you or another agent would need this fact, log it now.

Moments to log:

- **Decision made** — King says "let's go with raw TypeScript over React":
  ```
  kd tk log ab12 "Decision: raw TypeScript, not React — King's call

  Rationale: we want full control over the build pipeline without
  React's abstraction layer. This means we'll need to handle routing
  and state management ourselves, but the bundle size stays minimal
  and we avoid the React upgrade treadmill.

  Affected tickets: may need to revisit ab34 (component library choice)"
  ```

- **Root cause discovered** — agent traces a bug to an unexpected place:
  ```
  kd tk log ab12 "Root cause: stale cache in render_template()

  The DB query was a red herring — render_template() caches the compiled
  template and never invalidates when the schema changes. Found by tracing
  the actual SQL output, which was correct. The fix is to add a cache key
  that includes the schema version.

  Affected files: src/kingdom/render.py, src/kingdom/cache.py"
  ```

- **Scope change** — work expands or shifts mid-ticket:
  ```
  kd tk log ab12 "Scope change: also need to update the migration script
  ..."
  ```

- **Blocker cleared** — something that was stuck is now unblocked:
  ```
  kd tk log ab12 "Unblocked: upstream API now returns correct schema
  ..."
  ```

Rich, multi-line log entries are encouraged — a worklog entry is a place to dump everything you know in the moment, not a tweet. The `...` in the shorter examples means the agent should elaborate with full context.

### 3. Expand the Quick-Ref with realistic flag usage

The existing Quick-Ref shows bare commands. Expand the flag-heavy ones with common combos:

```
kd tk create "title"                                    # minimal
kd tk create -t bug -p 2 -d "details" "title"           # bug with priority and description
kd tk create --backlog "title"                           # backlog ticket
kd tk create --backlog -p 1 --ac "criterion" "title"     # full backlog ticket
kd council ask "prompt"                                  # all members
kd council ask --to claude "prompt"                      # single member
kd peasant start ab12                                    # worktree
kd peasant start ab12 --hand                             # serial in cwd
```

Skip obvious commands that don't need examples (`kd tk close ab12`, `kd tk show ab12`).

### 4. Workflow reflexes

A few decision patterns agents consistently get wrong:

- **Default to the active ticket.** If the agent is working a ticket, that's the target for `kd tk log`, `kd tk close`, and status updates. Don't ask "which ticket?" when context is obvious.
- **Move vs create.** "This work belongs somewhere else" → `kd tk move <id> --to backlog`. "This is a separate problem I just noticed" → `kd tk create --backlog "..."`. Log is for new information about the current work; create/move is for separate work.
- **Council follow-through.** After `kd council ask`, the agent should: summarize the key perspectives and disagreements, log the decision that came out of it (`kd tk log`), and move on. Don't dump the council response and wait for the King to synthesize.
- **Close-out.** Before `kd tk close`: update the worklog with what changed and how it was verified, confirm tests pass. Closing is the last step after evidence is captured, not a declaration of intent.

### 5. Error recovery ("When `kd` says no")

The skill currently teaches happy-path commands but nothing about what to do when they fail. That's exactly when agents either retry blindly, give up and ask the King, or silently move on. A few concrete recovery patterns:

- `kd tk close` fails because deps aren't met → inspect with `kd tk deps tree <id>`, figure out what's blocking, work the blocker or tell the King
- No obvious active ticket → `kd tk current` to check, don't guess
- `kd council ask` times out or errors → `kd council retry <thread>`, don't re-run the same ask from scratch
- `kd peasant start` fails because ticket isn't started → `kd tk start <id>` first, then retry
- Peasant seems stuck or broken → check `kd peasant status` / `kd peasant logs <id>` before escalating

The pattern is: diagnose before retrying, and never silently drop a failed operation.

### 6. Permission carve-out for proactive hygiene

The current skill says "only run state-modifying `kd` commands when the King explicitly asks." That conflicts with the proactive worklog and dogfooding behaviors this ticket adds. The skill needs an explicit carve-out:

**Allowed without explicit permission:**
- `kd tk log` — routine worklog updates on the active ticket (durable state changes, decisions, discoveries)
- `kd tk create --backlog` — filing dogfooding tickets when the agent notices a real UX issue while using `kd`

**Still requires explicit direction:**
- `kd tk close` / `kd tk move` / `kd tk start` — state transitions that change what work is active
- `kd council ask` — initiating a council discussion
- `kd peasant start` — launching parallel work

The line is: documenting what happened is always safe; changing what happens next needs the King's say-so.

### 7. Dogfooding reflex

CLAUDE.md already says "when you notice something off, immediately file a backlog ticket." The skill should teach this as a concrete behavior: if using `kd` exposes a real UX problem — confusing output, missing information, unnatural workflow — file it immediately:

```
kd tk create --backlog -t bug "UX: kd tk list output doesn't show ticket type"
```

This is a secondary reflex, not a core workflow step. Keep it to a short paragraph in the skill, not a full section. The bar is "real UX problem noticed during actual use," not "hypothetical improvement idea."

### 8. Don't invent defaults

Avoid hardcoding priority or other fields in examples unless the conversation justifies them. Show the agent using flags when the user supplies the info, not guessing.
