# Enrich harness worklog entries for real peasant observability

## Problem

Peasant work is a black box. You kick one off and have no idea what's happening until it's done (or broken). The current `kd peasant watch` output is useless — you can't see what the King asked, what the peasant did, why the council blocked it, what changed to fix it, or why it was eventually approved.

### What it actually looks like today

```
- [13:19] — Iteration 1/50 — calling agent
- [13:22] — ## What I did this iteration
- [13:26] — Council review: BLOCKING (bounce 1/3) — returning to working
- [13:26] — Iteration 2/50 — calling agent
- [13:28] — ## What I did this iteration
- [13:29] — Council review: APPROVED — awaiting king review
```

No idea what the agent did. No idea what the council reviewed. No idea why it was blocked the first time, or what changed to get it approved the second time. Just vibes.

### What it should look like

During a peasant run, the King should be able to answer: **"what is it doing, why, what changed, and why did council approve/block"** — without opening code or guessing.

## Approach: make the harness stop being lossy

The harness already sits at every interesting decision point. It knows the King's original prompt, it receives the agent's result, it submits to council and gets each member's verdict + reasoning, and it decides to loop or finish. The data is already in hand — `append_worklog` just throws away 90% of it.

**The fix is to enrich the existing `append_worklog` calls, not to build a new event system.** No new hooks, no agent-side changes, no structured event architecture. The agent stays completely unaware of observability.

### What each worklog entry should include

1. **Iteration start** — King's original prompt (first iteration) or council bounce feedback (subsequent iterations)
2. **Agent result** — Summary of what the agent did, not just "## What I did this iteration"
3. **File changes** — `git diff --stat` between iterations (cheap, no agent involvement)
4. **Council review** — Each member's verdict AND reasoning. "BLOCKING" with no reason is useless; include why it blocked and what it asked the peasant to fix
5. **Council approval** — Why it was approved, not just "APPROVED"

### Concrete touch points

Five changes across two files. No new abstractions, no agent-side changes.

1. **`run_council_review` — stop discarding approval reasoning** (`src/kingdom/harness.py`). Today it returns `("approved", [])` — approval text is thrown away, only blocking feedback is collected. Fix: collect `(name, response.text)` for *all* members regardless of verdict, return `(outcome, feedback)` where feedback always has content. Same return shape, just populated for both outcomes.

2. **Harness worklog callsites — format summaries inline** (`src/kingdom/harness.py`). At the approved/blocking write sites, build a summary from the feedback list: truncate each member's text to first line / ~120 chars for the worklog entry. The bounce path keeps using full text as it already does. One small `summarize_feedback()` helper at the write site.

3. **`append_worklog_entry` — indent continuation lines** (`src/kingdom/ticket.py`). Today it writes `- [timestamp] — message` with no multiline handling. Fix: indent continuation lines by 2 spaces so multiline entries (council reasoning, diff stats) render as grouped bullets in markdown and in watch.

4. **Harness post-agent — add `git diff --stat`** (`src/kingdom/harness.py`). After the agent returns and its (often useless) worklog entry is written, run `git diff --stat HEAD~1` in the worktree and append a "Files changed:" worklog entry. This supplements the agent's lossy summary with concrete data about what actually moved. The harness already knows the worktree path. Costs one subprocess call that takes milliseconds.

5. **Watch — no changes needed in first pass.** Indented continuation lines from touch point 3 will render correctly with the existing `console.print(line)` loop. Grouped-entry printing (detecting `- [` as entry boundaries) is a natural follow-up if needed.

### What stays the same

- Tmux mode (`kd peasant start --tmux`) stays as-is for "show me the raw Claude Code session" — useful for debugging but not the primary observability mechanism
- No new files, no new event streams, no new polling mechanisms

The watch loop (~line 528) currently only tails the worklog. Add a parallel poll of the peasant worktree (path via `worktree_path_for()`). Every 30-60 seconds, run `git status --short` and `git diff --stat` in the worktree. Print deltas as indented, un-bulleted lines visually distinct from worklog entries:

```
- [03:50] — Iteration 1/50 — calling agent
  Ticket: kd tk list: show closed ticket count when no open tickets remain

  [03:51] worktree: M src/kingdom/cli/ticket.py
```
