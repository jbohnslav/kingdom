# Update the peasant prompt harness

Started as a peasant prompt rewrite — the system prompt was nearly empty. Expanded into a full prompt audit after finding the same problems across the council and review surfaces.

## Round 1: Peasant Prompt (done)

The peasant system prompt was 15 lines with no Kingdom context, no work instructions, no worklog guidance, no response format that produces useful watch output. Rewrote to teach the peasant its job.

- [x] Prompt explains what Kingdom is (King assigns, peasant implements, council reviews, bounces on block)
- [x] Prompt tells peasant to read ticket thoroughly and understand acceptance criteria before coding
- [x] Prompt tells peasant to update worklog with important decisions and King input via kd tk log or direct edits
- [x] Prompt tells peasant to use BLOCKED instead of spinning when stuck
- [x] Response format produces useful first-paragraph summaries for kd peasant watch (no headings, no numbered lists)
- [x] Prompt is natural language, not a config file — reads like a briefing
- [x] No hardcoded language-specific tools (no pytest, ruff, etc.) — agent learns tools from CLAUDE.md

## Round 2: Prompt Audit Findings

Full audit of all prompt surfaces found three more gaps:

### A. Council chat suffix is too weak (biggest gap)

The entire instruction for council members in a group discussion is:
```
You are {member}. Continue the discussion.
```
(`src/kingdom/thread.py:536`)

No guidance on reading the full thread, engaging with prior agents, referencing specific points, agreeing/disagreeing directly. Without this, each member answers the King's question independently — parallel monologues instead of a group discussion. The King had to manually supply these rules as a system prompt for this session to work.

- [ ] Council chat suffix tells members to read the full thread before responding
- [ ] Members are told to engage with what others have said — agree, disagree, extend, synthesize
- [ ] Members are told not to answer in isolation but to reference specific prior points
- [ ] Natural language tone, not boilerplate

### B. Agent-facing review prompts are inconsistent

The split-brain problem is real, but the right split is by audience:

- **Human-facing**: `kd peasant review` is a guided tour for the King and should stay separate.
- **Agent-facing**: harness council review and `kd council review` should share one review-task contract.

Today those two agent-facing paths are inconsistent:

1. **The harness review** (`build_review_prompt` at `harness.py:441-485`) pastes the entire diff inline. For large changes, that's hundreds of prompt lines consumed before the reviewer starts thinking.
2. **The CLI `kd council review`** (`council.py:403-412`) is too thin — almost no context at all, just "review the changes" with a commit log and `--stat`.

Neither is right. These are coding agents — they can inspect code themselves. The shared review prompt should tell them where to look, how to inspect, what standard to apply, and what format to return.

The shared agent-facing review prompt should include:
- Ticket path and title when a current ticket exists
- Branch name and scope / base context
- Changed file list (names only, not the full diff)
- Suggested commands: `git diff`, `git show`, `git log`, `kd tk show`
- Review standard: correctness, tests, regressions, acceptance criteria
- Required output: `VERDICT: APPROVED` or `VERDICT: BLOCKING` with reasoning

- [ ] One shared agent-facing review prompt builder used by both harness council review and `kd council review`
- [ ] Agent-facing review prompts do NOT paste the full diff by default — they point reviewers at the code and let them investigate
- [ ] Shared review prompt includes ticket/worklog/acceptance-criteria context when a current ticket exists, but still works for branch-only reviews without a ticket
- [ ] Both agent-facing review paths require a `VERDICT:` line
- [ ] `kd peasant review` remains a separate human-facing guided-tour path and is not folded into prompt unification

### C. `prompts.review` config slot is dead code

`prompts.review` is in the config schema (`config.py:38`), documented, validated — and never consumed at runtime. The same is true for agent-specific review overrides under `agents.<name>.prompts.review`. Users who configure either are being silently ignored.

- [ ] `prompts.review` is either wired into the shared agent-facing review prompt (prepended like `prompts.council` is for council commands) or removed from the config schema
- [ ] If wired in, both review paths consume the global `prompts.review`
- [ ] If wired in, agent-specific `agents.<name>.prompts.review` overrides are also respected in both review paths
- [ ] Regression tests cover global and per-agent review prompt wiring so this cannot silently drift again
