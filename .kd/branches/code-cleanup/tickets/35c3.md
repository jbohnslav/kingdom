# Peasant watch: stream live agent output and fix worktree worklog path

## Problem

Peasant watch goes dark for 3-15 minutes during agent execution. The King sees
nothing but "Still working..." heartbeats while the agent is actively reading
files, editing code, running tests, and making decisions. This makes peasants
feel broken and untrustworthy.

### Raw watch output that triggered this investigation

```
Watching peasant-226c  (Ctrl+C to stop)

- [20:20] — Iteration 1/50 — calling agent
  Ticket: kd tk list: show dep status (open/closed) in Deps column
  [20:21] Editing rc/kingdom/cli/ticket.py
  Still working... 1m since last activity
  [20:22] Editing rc/kingdom/cli/ticket.py
  [20:22] Editing tests/test_cli_ticket.py
  Still working... 1m since last activity
  Still working... 2m since last activity
  Still working... 3m since last activity
  Still working... 4m since last activity
  Still working... 5m since last activity
  Still working... 6m since last activity
  [20:35] Committed f569bd0 "feat: annotate dep status in kd tk list Deps column"
```

13 minutes of silence between the last file edit and the commit. The agent was
busy the entire time (52 turns, 16 min) — reading code, running tests, checking
linting. All invisible.

## Root Cause Analysis

Two independent bugs compound into the dead zone:

### Bug 1: stdout log is not real-time

The harness uses `subprocess.run(..., capture_output=True)` (harness.py:822-831).
This buffers ALL agent output in memory and only dumps it to
`.kd/branches/{branch}/logs/peasant-{id}/stdout.log` AFTER the process exits.
The log file is empty during execution, so watch can't tail it.

Evidence from the stdout log:
- 20:20:01 "Calling backend"
- 20:36:06 "Agent stdout" (16 minutes of output dumped at once)

### Bug 2: all `kd` commands from worktree agents resolve against the wrong project root

The prompt at harness.py:110-116 tells the agent to run
`kd tk log {ticket_id} "message"`. The agent runs with cwd=worktree (line 828).
`find_project_root()` (state.py:71-97) checks cwd first, finds `.kd/` in the
worktree's copy of the repo, and uses that. Every `kd` command the agent runs —
not just `kd tk log` — resolves against the worktree's `.kd/` instead of the
main repo's.

The harness spawns agents via `clean_agent_env()` (agent.py:438-453), which
strips `CLAUDECODE` and injects `KD_ROLE`/`KD_AGENT_NAME` — but never sets
`KD_BASE`. So `find_project_root()` falls through to the cwd fast path every
time.

Evidence: `.kd/worktrees/226c/.kd/backlog/tickets/226c.md` has two worklog
entries the agent faithfully wrote — the main repo's `226c.md` never saw them.

**Caution on the fix:** `find_project_root()` already has a carefully ordered
resolution chain (KD_BASE → cwd → parent walk → git toplevel) that handles
monorepo subdirectories. If you're working in `monorepo/service-a/` and the
`.kd/` lives at `monorepo/.kd/`, the parent walk finds it correctly. The fix
here is NOT to change `find_project_root()` itself — it's to have the harness
set `KD_BASE` in the agent's environment pointing to the real project root
before spawning the subprocess. That way `find_project_root()` short-circuits
at step 1 (line 86-91) and the parent walk / cwd logic is never reached.

## Solution

Two fixes, ordered by priority. Fix 1 restores the mechanism that's *supposed*
to work already (worklogs). Fix 2 adds deeper mid-turn visibility for the long
stretches where the agent is reading/thinking rather than logging.

### Fix 1 (first): Set KD_BASE in harness agent environment

Have `clean_agent_env()` (agent.py:448) or the harness call site (harness.py:830)
inject `KD_BASE=<main repo root>` into the agent's environment. This makes every
`kd` command the agent runs — `kd tk log`, `kd tk show`, anything — resolve
against the main repo's `.kd/`, not the worktree's copy.

This is the higher-priority fix because the worklog mechanism already exists: the
prompt tells the agent to log, the agent does log, and watch already knows how to
display worklog entries. It's just plumbing to the wrong file. Fixing this one
env var gives you incremental worklog updates for free — no harness subprocess
changes required.

**Do not change `find_project_root()` itself.** Its resolution chain already
handles monorepo subdirectories correctly (parent walk finds `.kd/` up the tree).
The King hit a prior bug where working in `monorepo/service-a/` would create a
spurious `.kd/` in the subdirectory. The fix must be injecting `KD_BASE` from the
harness so `find_project_root()` short-circuits at step 1 (state.py:86-91), not
altering the resolution chain.

### Fix 2 (then): Stream agent stdout in real time

Replace `subprocess.run(..., capture_output=True)` with `Popen` + streaming.
Pipe stdout/stderr to the log file line-by-line in real time. Then have peasant
watch tail that log file every ~15s and display recent human-readable lines.

**Streaming must be additive, not a replacement.** Accumulate full stdout/stderr
buffers alongside the live stream so `parse_response()` (harness.py:856) still
works. Resume behavior and session ID recovery depend on having the complete
output after the child exits. Break this and peasants can't resume.

**Watch tailing needs filtering.** Raw agent CLI output is noisy — ANSI escapes,
JSON blobs, tool call metadata. Watch should strip/summarize before displaying:
skip lines that are pure JSON or ANSI control sequences, grab the last 2-3
human-readable lines, truncate each to ~200 chars. Otherwise watch goes from
"no information" to "too much noise," which is a different version of the same
problem.

Target behavior: durable progress comes from real `kd tk log` entries landing in
the shared branch ticket (Fix 1). Ephemeral live progress comes from tailed child
stdout when the agent is reading, thinking, or running tests (Fix 2). Together
they give you both a trustworthy worklog and a watch command that feels alive.

### What not to do

- **Don't add peasant phases or a state machine.** The King rejected this as
  overengineered. The fix is plumbing, not architecture.
- **Don't patch only `kd tk log`.** That leaves the underlying worktree/shared-
  state split in place for every other `kd` command.
- **Don't reduce the worktree poll interval as the primary fix.** That only makes
  "Editing ..." show up slightly sooner; it does nothing for a 13-minute opaque
  agent turn where no files change.
- **Don't change `find_project_root()` resolution order.** That reopens the
  monorepo/subdirectory bug.

## How we got here

The council (claude, codex) analyzed the watch code path and identified the
heartbeat-only design. Claude initially suggested tailing the stdout log as a
cheap win, then corrected himself after discovering capture_output=True makes
the log file empty during execution. The worktree path bug was discovered by
checking the 226c worktree's ticket file and finding worklog entries that never
appeared in the main repo copy. The King rejected Codex's "peasant phases"
proposal as overengineered — the fix should be plumbing, not a state machine.

Codex reviewed the initial ticket and caught two issues: (1) Bug 2 was scoped
too narrowly to `kd tk log` when the real seam is `find_project_root()` — any
`kd` command from a worktree hits the same problem because `clean_agent_env()`
never sets `KD_BASE`; (2) the streaming fix needs an explicit AC preserving
`parse_response()` semantics so resume/session recovery doesn't regress. The
King confirmed the project root resolution is the right focus, noting a prior
monorepo subdirectory bug where `find_project_root()` would pick up a nested
`.kd/` — the fix must be injecting `KD_BASE` from the harness, not changing the
resolution chain itself.
