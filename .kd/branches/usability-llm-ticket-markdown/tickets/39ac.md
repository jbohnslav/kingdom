# Multi-workspace support: long-lived worktrees + peasant sandboxes

Support running kd across multiple long-lived human worktrees (e.g. evals, data, training) within the same repo, while peasants continue using short-lived per-ticket worktrees.

## Acceptance Criteria

- [x] `kd` can discover repo-local `.kd/` from a manual sibling git worktree that lacks `.kd/`
- [x] Discovery uses `KD_BASE`, parent `.kd/`, current git root `.kd/`, then `git worktree list --porcelain` sibling lookup
- [x] Ambiguous sibling `.kd/` owners fail loudly and tell the user to set `KD_BASE`
- [x] Git operations in peasant flows run against the invocation worktree, not blindly against the `.kd/` owner checkout
- [x] Current worktree git branch takes precedence over shared `.kd/current`; `.kd/current` is a fallback/default
- [x] Peasant worktrees are namespaced by parent branch/workspace (for example `.kd/worktrees/<branch>/<ticket>`) so parallel workspaces do not collide
- [x] Existing legacy `.kd/worktrees/<ticket>` paths remain readable for cleanup/watch/reject/sync
- [x] Kingdom never creates or cleans up long-lived human worktrees; it only manages peasant sandboxes
- [x] No new top-level `project` or `workstream` abstraction is added; branch remains the planning unit

## Design Notes (from council discussion)

### Two-tier worktree model

Claude's main point is right: distinguish **long-lived human worktrees** from **short-lived peasant worktrees**. Human worktrees are King-managed and durable. Peasant worktrees are disposable execution sandboxes for tickets.

### Scope

Codex's pushback on the original framing: a path fix alone is not enough. If `kd peasant watch` and related runtime state stay checkout-local, the git model works but the product still feels broken across multiple human worktrees.

Keep this small:

1. Use git common dir for peasant worktree path resolution.
2. Namespace peasant worktrees by parent branch/workspace.
3. Share only the runtime state that needs to be repo-visible across long-lived worktrees, such as peasant activity/watch metadata.
4. Leave tracked planning artifacts branch-scoped as they are now.

### What NOT to build

Both agents agreed: do not invent a new `project` or `workstream` model yet. Branch already does the planning job. This ticket is about making the execution/runtime layer work cleanly inside multiple long-lived worktrees.

### Approach (least invasive)

1. Resolve peasant worktree paths from git common dir instead of the current checkout.
2. Put peasant worktrees under a namespaced repo-shared path.
3. Make peasant runtime/watch state visible across long-lived worktrees.
4. Do not add a new top-level command or abstraction in this ticket.

### Council Review (2026-03-06)

Second council review focused on implementation readiness. Key findings:

**It mostly works already.** Real-world testing shows kd commands work fine from a human worktree because `.kd/` is tracked in git and present in every checkout. The original concern about `find_project_root()` failing was unfounded.

**What's actually broken:** Only gitignored runtime state (sessions, logs, peasant worktrees) is checkout-local. Peasants started from worktree A won't appear in `kd peasant status` from worktree B. This only matters if you need cross-worktree peasant visibility.

**Blast radius if we do it:** Larger than expected — state.py, worktree.py, session.py, peasant.py, harness.py, cli/__init__.py, ticket.py all touch path resolution. Codex counted ~81 call sites across 10 files.

**Codex recommendation:** Two-root model — checkout-local root for tracked `.kd/` artifacts, shared runtime root (under `git common dir`) for peasant state. Keep `.kd/current` checkout-local so worktrees don't fight.

**Claude recommendation:** Decompose into sub-tickets: (A) fix `find_project_root()` to use `--git-common-dir` [low risk], (B) namespace peasant worktrees by branch [medium risk], (C) shared runtime sessions [defer unless needed]. Watch out for `--git-common-dir` returning relative paths from main checkout vs absolute from worktrees.

**Missing from ACs:** Migration story for existing worktrees, relative vs absolute `--git-common-dir` handling, verify `KD_BASE` injection in harness.py.

**Decision:** Deprioritized to P3/backlog. No concrete breakage in current usage — this is a robustness improvement for when cross-worktree peasant visibility is actually needed.

### Council Review (2026-04-30)

Asked the council how to make `.kd/` discoverable from manual worktrees that do not have `.kd/` checked out. Claude rate-limited; Codex recommended keeping `.kd/` repo-local and separating the `.kd` owner checkout from the invocation worktree.

Decision:

1. Keep tracked Kingdom state in repo-local `.kd/`.
2. Locate a sibling `.kd/` owner with `git worktree list --porcelain`; `git rev-parse --git-common-dir` alone is not enough because it finds shared git metadata, not the checkout that owns `.kd/`.
3. Treat `.kd/current` as a fallback/default. The branch of the worktree where `kd` is invoked should win when it maps to a tracked Kingdom branch.
4. Avoid a new global `~/.kd` project registry or new `project`/`workstream` abstraction.
