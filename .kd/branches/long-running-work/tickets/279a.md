# Worklog entries lack author attribution, polluting lord context

## Problem

Worklog entries have no author information. When the lord or `kd lord watch` reads the epic worklog, King/Hand entries are indistinguishable from lord entries. This wastes lord context on entries it didn't write and can't act on.

## Write paths that need tagging

All worklog write paths must tag entries with an author:

1. **`kd tk log`** (cli/ticket.py:1384) — uses `append_worklog_entry` directly. Author comes from `KD_ROLE` env var (already inferred at cli/__init__.py:466-469): `king`, `hand`, or agent name.
2. **`append_lord_worklog`** (lord_harness.py:52) — always lord. Tag as `lord-<epic_id>` using the existing `lord_session_name()` helper.
3. **`append_worklog`** (harness.py:214) — peasant harness. Tag as `peasant-<ticket_id>`.

## Entry format

Current: `- [HH:MM] — message`
New: `- [HH:MM] [author] — message`

Example: `- [14:32] [lord-4d4a] — started peasant on 57e2`

## Legacy entries

Existing entries use the old `- [HH:MM] — ...` format with no author tag. The filter should treat untagged entries as `unknown` and include them by default (don't silently drop history). Over time they'll scroll off naturally.

## Read paths that need filtering

1. **`kd lord watch`** (cli/lord.py:312) — filter to `lord-*` + `unknown` entries by default.
2. `--all` flag shows unfiltered view (all authors).

Note: lord prompt worklog restoration is a separate ticket (depends on this one). This ticket focuses on the write-side tagging and `kd lord watch` filtering.

## Acceptance Criteria

- [ ] `append_worklog_entry` accepts an optional `author` param, formats as `[author]` after timestamp
- [ ] `kd tk log` infers author from `KD_ROLE`/`KD_AGENT_NAME` and passes it through
- [ ] `append_lord_worklog` tags entries as `lord-<epic_id>`
- [ ] `append_worklog` (peasant harness) tags entries as `peasant-<ticket_id>`
- [ ] `kd lord watch` filters to `lord-*` + `unknown` entries by default
- [ ] `--all` flag on `kd lord watch` shows unfiltered worklog
- [ ] Untagged legacy entries are treated as `unknown` and included by default
- [ ] Tests cover tagged entry formatting, legacy entry parsing, and default vs `--all` filtering
