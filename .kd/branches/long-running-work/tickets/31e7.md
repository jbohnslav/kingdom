# Improve peasant accept merge conflict workflow and recovery

The current peasant accept flow breaks badly on merge conflicts:

1. accept tries to merge ticket/<id> into the feature branch
2. If conflict, it exits code 1 and tells you to resolve in the worktree — but that's backwards (the merge happens on the feature branch, not in the worktree)
3. After manual resolution, accept can't be re-run because it blindly retries the merge
4. This leads to manual cleanup (kd tk close + kd peasant clean --force) which bypasses session state updates

What went wrong in practice:
- Uncommitted ticket file changes on long-running-work caused the merge to be messy
- The recovery steps in the error message are confusing (says cd into worktree, but the conflict is on the feature branch)
- After manually resolving and committing the merge, there's no way to tell accept 'merge is done, just do the cleanup'

Needs:
- Document the correct flow: commit/stash feature branch changes BEFORE running accept
- Make accept idempotent: if the worktree branch is already merged, skip the merge and proceed with cleanup (close ticket, update session, remove worktree)
- Fix the error message recovery steps to match what actually needs to happen
- Update the skill (SKILL.md) so agents (lord, Hand) know the right conflict resolution flow

## Acceptance Criteria

- [ ] kd peasant accept is idempotent — if worktree branch already merged, skips merge and does cleanup
- [ ] Error message recovery steps accurately describe how to resolve conflicts
- [ ] SKILL.md documents the correct merge conflict workflow for agents
- [ ] Uncommitted changes on feature branch are handled gracefully (warn or stash before merge)
