# Restore bounded worklog context to lord prompt

The lord prompt currently strips everything below '## Worklog' in the epic body (lord_harness.py build_lord_prompt). This was a defensive measure when the worklog was noisy with idle-cycle narration. Now that worklog hygiene is improved (0aa6, 2ca9) and author tagging is landing (279a), the lord should get its worklog context back — it's the lord's durable memory between cycles. Without it, the lord re-derives context from ticket statuses alone and can repeat actions or make inconsistent decisions.

The fix is not 'stop stripping' — codex is right that unbounded worklog in the prompt recreates growth problems. Instead: replace the blunt strip with a bounded, filtered slice of lord-authored entries (e.g., last N entries or token budget). This gives the lord its decision history without making prompt size unbounded.

## Implementation

1. After 279a lands author tagging, filter epic worklog to lord-* and unknown entries
2. Take the most recent N entries (or entries within a token/char budget) as the lord's 'recent memory'
3. Inject this bounded slice into the lord prompt where the worklog section used to be
4. Remove the blunt '## Worklog' strip

## Acceptance Criteria

- [ ] Lord prompt includes a bounded, filtered worklog section instead of stripping it entirely
- [ ] Only lord-* and unknown (legacy) entries are included by default
- [ ] Worklog context is bounded (recent N entries or token budget) to prevent prompt growth
- [ ] Lord can reference its own prior decisions from the worklog context
- [ ] Tests cover filtering, bounding, and prompt assembly with worklog context
