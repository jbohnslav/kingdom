# Epic support: hierarchical ticket decomposition

Add epic support to the ticket system. An epic is a ticket with `type=epic` — an explicit opt-in label. Any ticket can have children via the existing `parent` field, but only `type=epic` tickets get epic-specific guardrails (peasant rejection, close enforcement). No new entity or storage model.

Key changes:
1. Validate ticket type on create/update against a known set (task, bug, feature, epic). Currently accepts any string.
2. Add `kd tk list --parent <id>` to list children of a ticket.
3. Add aggregate child status to the existing Children section in `kd tk show` (e.g. "3/5 closed"). Children already render; this adds the rollup.
4. Guard `kd peasant start` against `type=epic` tickets (epics aren't atomic work units).
5. `kd tk close` on a `type=epic` ticket refuses if children are still open (not just a warning — hard block). Note: `kd done` already blocks on open branch tickets, so no separate check needed there.

Non-goals:
- No separate Epic model or storage — epics are tickets
- No dependency changes — deps remain between individual tickets only
- No automatic epic suggestion or detection in the skill
- No special backlog treatment for epics
- No `kd tk split` command in the first version
- No epic-specific behavior for non-epic tickets that happen to have children

## Acceptance Criteria

- [ ] Ticket type validated against known set (task, bug, feature, epic) on create and update
