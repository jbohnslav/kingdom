# Council queries should create new threads by default

When an agent (e.g. peasant) runs 'kd council ask', it reuses the existing thread for that branch. If a human is actively chatting with the council in an interactive window, the agent's query overwrites the conversation in real time — you can literally watch it happen. Council queries should default to creating a new thread so they don't stomp on active conversations. The current thread could be an explicit --thread/--continue flag instead.

## Design (council-approved)

### Implementation plan
1. Flip default in `council.py` — always new thread unless `--continue`
2. Add `--continue` / `-c` flag, remove `--new-thread`
3. Hard error on `--continue` with no current thread (actionable message)
4. `council review` already passes `new_thread=True` — drop that arg (now default)
5. Update docs: `SKILL.md`, `references/council.md`, `docs/multi-agent-design-v3.md`
6. Update tests in `test_cli_council.py`

### Key findings
- Peasant auto-reviews go through `run_council_review()` in harness.py, bypassing `council_ask()`. However, the King has observed peasant review threads stomping on interactive council chats — so verify the harness thread isolation is actually working before assuming no changes needed there.
- Council "threads" (saved conversation files) and backend agent "sessions" (resume IDs) are separate. New thread doesn't reset model memory. This is probably fine but worth being aware of.
