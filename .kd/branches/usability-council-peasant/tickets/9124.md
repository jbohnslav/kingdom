# Add error/complete metadata to thread message frontmatter

## Context

From 6412 council review: when an agent times out with partial text, `thread_body()` returns just the text (no error marker). This means `council retry` can't distinguish a full response from a partial one cut off by timeout.

Currently acceptable because timeouts are non-retriable and users see the timeout in watch output. But when building richer thread semantics (chat TUI, group chat, thread history injection), proper message metadata will be needed.

## Design (updated per design doc)

Add optional `status` field to assistant message YAML frontmatter. Values: `complete`, `error`, `timeout`, `interrupted`. No separate `error` or `complete` booleans — status alone is sufficient.

Example partial-timeout message:
```yaml
---
from: claude
to: king
timestamp: 2026-02-15T10:30:45Z
status: timeout
---

Partial response text here...
```

## Acceptance Criteria

- [ ] Add optional `status` field to `Message` dataclass (default `None` for backward compat)
- [ ] Update `add_message()` to accept and serialize optional status field
- [ ] Update `parse_message()` to read status from frontmatter (backward-compatible with existing messages)
- [ ] Update `AgentResponse.thread_body()` to always return text; pass status metadata separately
- [ ] Update `council retry` to check `msg.status` first, fall back to body prefix for legacy messages
- [ ] Update `council show` / `render_response` to surface status when metadata present
- [ ] Test: retry after timeout status should re-query
- [ ] Test: retry after complete status should not re-query
- [ ] Test: legacy thread with `*Error:` body and no status still retries
- [ ] Test: mixed thread (some with status, some legacy) behaves deterministically
