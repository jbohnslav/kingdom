# Rewrite kingdom skill for brevity and readability

The SKILL.md has grown organically and needs a rewrite. It's currently 170+ lines with verbose tables and repetitive sections.

## Goal

Rewrite SKILL.md as a **playbook** (how to work) rather than a **reference manual** (what commands exist). Agents loading the skill should immediately understand which workflow they're in and how to operate. Push command syntax details to `references/` files.

## Structure

### 1. Intro (2 lines)
- You're helping the King build software using `kd`. Two common workflows below.

### 2. Safety
- Keep the existing "never modify without asking" rule verbatim.

### 3. Workflow A: New Feature (design-first)
- `git checkout -b <branch>` → `kd start` → `kd design` → iterate with council → `kd design approve` → `kd breakdown` → work tickets
- The design phase is collaborative: King drives, agent drafts, council reviews.

### 4. Workflow B: Backlog Sprint (execution-first)
- `git checkout -b <branch>` → `kd start` → `kd tk pull <ids>` → work tickets → PR
- No design phase. Tickets are already scoped. If one is ambiguous, escalate — don't guess.

### 5. Executing Tickets (two equal options)
After workflows A or B produce a set of tickets, choose how to execute them:

**Option A: Single agent with King in the loop**
- Work tickets sequentially. The King guides priorities and reviews as you go.
- This is "normal coding" — no special commands beyond `kd tk start/close`.

**Option B: Peasant workers (parallel, autonomous)**
- `kd peasant start <id>` spawns a background worker per ticket in its own worktree.
- Each peasant implements, council reviews automatically, peasant iterates until approved.
- The King monitors with `kd peasant status` / `kd watch`.
- See `references/peasants.md` for details.

Both are first-class. Use A when the King wants to be hands-on; use B for throughput on well-scoped tickets.

### 6. Working a Ticket (applies to both execution modes)
Use the King's standard block nearly verbatim:

- **One at a time**: `kd tk start` → do the work → `kd tk close` → commit → next ticket.
- **Worklog**: append progress notes to the ticket's `## Worklog` section as you go.
- **Acceptance criteria**: only close when all AC are met.
- **Decisions**: ask the King or consult the council (`kd council ask`) for difficult design decisions — don't guess.
- **For bugs: test BEFORE you fix!** Write a failing test first, fix it, verify.
- **Bugs from this branch**: immediately write a failing test that reproduces it, then fix.
- **Bugs from elsewhere**: if not blocking, `kd tk create --backlog "..."` and move on.
- **Commit often**: commit code changes as you go.
- **One-off tests**: write a script or temp file to test e2e with real data, then consider automating as an integration test.
- **Dogfooding**: notice UX issues with `kd` itself? File a backlog ticket immediately.

### 7. Council (compressed, 3-4 lines)
- `kd council ask "prompt"` for multi-model perspectives.
- Use it proactively at decision points, not just when stuck.
- Pointer to `references/council.md` for flags and threading details.

### 8. Command Quick-Ref- Terse list: `kd start`, `kd design`, `kd breakdown`, `kd tk <sub>`, `kd council ask`, `kd done`.
- No flags, no detailed syntax — reference files cover that.

### 9. References- Links to `references/tickets.md`, `references/council.md`, `references/peasants.md`.

## What to cut
- ~30 lines of council threading mechanics, async flags, storage paths — all in references already.
- Verbose command tables with flag descriptions — agents can use `--help`.
- Repetitive content between SKILL.md and reference files.

## Key principles
- **Two execution modes, equal billing.** Single-agent with King and peasant workers are both first-class — present them as a choice, not default-vs-advanced.
- **Work log discipline is a first-class expectation**, not a footnote.
- **Escalation protocol is explicit**: never silently resolve ambiguity on architectural/product/UX decisions.
- **Trust the references**: don't duplicate their content in the skill.
