# Bug: kd chat scroll issues — pin-to-bottom broken + double scrollbars

## Description

Two issues in `kd chat`:

1. **Pin-to-bottom broken**: The auto-scroll that keeps the view pinned to the latest message doesn't work reliably. 603d attempted to fix this with a smart `is_following` mechanism but it's still not working correctly.

2. **Double scrollbars**: Two scrollbars appear on the right side of the chat. Likely the outer `Screen` and the inner `MessageLog` (or `VerticalScroll` container) are both showing scrollbars. Only the message log should scroll.

## Prior work

- 603d (closed, polish branch): Added `is_following` / anchor-based auto-scroll with `SCROLL_THRESHOLD`. Didn't fully resolve.

## Research / Root cause analysis

### Pin-to-bottom
Council (thread b5f1) identified two issues:
1. **Intent capture timing** (codex): `is_following` was checked AFTER mutations (e.g. mounts), but content changes shift `max_scroll_y` which makes the check unreliable. A single batched update can move the bottom by more than the threshold and flip follow to false even if the user was pinned. Fix: check `is_following` BEFORE mounts/updates.
2. **Multiple scroll calls per frame** (codex): Rapid streaming updates schedule dozens of competing `scroll_end` calls. Fix: coalesce via `_scroll_pending` flag.
3. **Deferred scroll** (claude, b5f1): `call_after_refresh` is necessary so `scroll_end()` runs after layout recomputes `max_scroll_y`, not before.

### Double scrollbars
Two real, functional scrollbar tracks visible on the right edge. The right one has a moving blue thumb — it's the Screen's scrollbar.

**What the King saw**: Two side-by-side scrollbar tracks at the right edge. Both functional — scrolling moves both thumbs. Persisted despite CSS overrides (`overflow-y: hidden`, `scrollbar-size: 0 0`) and inline style overrides in `on_mount`.

**What headless diagnostics showed**: `run_test()` reported `show_vertical_scrollbar=False` on Screen and only MessageLog had a scrollbar. SVG screenshot showed only one scrollbar column. The headless test did NOT reproduce the double scrollbar — misleading.

**What the council found** (threads b5f1 and cfed):
- **claude (b5f1, turn 2)**: CSS specificity between `App.CSS` and `Screen.DEFAULT_CSS` may be unresolved — Textual treats them as equal specificity, resolution depends on MRO order. Suggested ChatScreen subclass with its own `DEFAULT_CSS`.
- **codex (b5f1, turn 2)**: Confirmed at runtime Screen has `max_scroll_y=0`, `show_vertical_scrollbar=False` — but this was in headless mode, which didn't reproduce the real issue.
- **claude (cfed, turn 2)**: "Textual's Screen inherits scrollable behavior at the class level. Setting CSS properties hides the visual scrollbar but doesn't necessarily prevent the Screen from being a scroll container."
- **claude (cfed, turn 4, after web search)**: Found `allow_vertical_scroll` property in Widget API docs — "Check if vertical scroll is permitted. May be overridden." This is the Python-level control, not CSS. CSS controls are about **visibility**, not **behavior**. The CSS approach hides the scrollbar visual but doesn't stop the Screen from computing as a scroll container.
- **References**: Textual GitHub Discussion #2953 (Disable scrolling of parent), Issue #1201 (Programmatic scrolling with overflow hidden).

**Attempted fixes that did NOT work**:
1. `ChatApp.CSS`: `Screen { overflow-y: hidden; scrollbar-size: 0 0; }` — lost CSS specificity battle
2. Inline styles in `on_mount`: `self.screen.styles.overflow_y = "hidden"` etc. — no effect
3. `ChatScreen` subclass with `allow_vertical_scroll = False` — only blocks scroll *actions* (keyboard/mouse), not scrollbar *display* (claude cfed turn 6)
4. `ChatScreen.DEFAULT_CSS` with `overflow-y: hidden` — still didn't work in real terminal

**Runtime diagnostic from real terminal** (`/tmp/kd-chat-scrollbar-debug.txt`):
```
Screen: ChatScreen, vsb=False, overflow_y=hidden, max_scroll_y=0,
  virtual=Size(width=106, height=45), size=Size(width=106, height=45)
  SCROLLBAR: MessageLog#message-log overflow_y=auto
  virtual=Size(width=104, height=218) size=Size(width=106, height=41)
```
**The Screen has NO scrollbar in the real terminal either.** Only MessageLog has one. The "second scrollbar" is NOT from the Screen — it's a visual artifact. MessageLog's scrollbar is 2 cells wide (default `scrollbar-size-vertical: 2`). The 1-cell right margin of panels (`margin: 0 1`) is adjacent to the 2-cell scrollbar track. The different background colors (`$background` vs `$scrollbar-background`) create the illusion of two separate bars.

**King observation**: It is literally a second scrollbar with a thumb that moves independently from the first. NOT a shadow or visual artifact. Despite the runtime diagnostic reporting only one widget with `show_vertical_scrollbar=True`, there are two independently-moving scrollbar thumbs visible in the real terminal. The diagnostic may not be capturing the full picture — possibly a scrollbar is created/shown after the 2-second diagnostic delay, or the diagnostic query doesn't cover all widget types (e.g. virtual DOM scrollbar widgets).

**Comprehensive diagnostic** (second pass): Walked ALL widgets via `query("*")` and checked `_vertical_scrollbar` attribute (the lazy-initialized virtual DOM ScrollBar instance) on every widget, plus the Screen separately. Result: only ONE `_vertical_scrollbar` exists in the entire app — on `MessageLog#message-log`. The Screen doesn't even have one created (`_vertical_scrollbar=None`). No other widget has a scrollbar instance. Yet two independently-moving thumbs are visible in the real terminal.

**iTerm2 scrollbar comparison**: The King showed iTerm2's native scrollbar — it's a gray/silver capsule-shaped overlay on the right edge, thin and rounded. The mystery second scrollbar in `kd chat` does NOT look like iTerm2's native scrollbar. It has a dark track with a blue thumb, identical in style to Textual's scrollbar rendering. Two possible explanations remain:
1. iTerm2 renders its alternate-screen scrollbar differently from its normal scrollbar (unverified)
2. There is a Textual rendering path that creates a second scrollbar column not tracked by `_vertical_scrollbar` (e.g. a gutter/track column rendered by the layout engine independent of the ScrollBar widget)

**Resolution**: Confirmed iTerm2-specific. The second scrollbar does NOT appear in macOS Terminal.app. iTerm2 shows its own scrollbar alongside Textual's MessageLog scrollbar when running alternate-screen apps. Despite looking like a Textual scrollbar (dark track, blue-ish thumb), it's iTerm2 rendering its scrollbar in alternate-screen mode with a style that mimics the terminal content.

**Workaround**: iTerm2 → Preferences → Appearance → Windows → "Hide scrollbars". This hides iTerm2's scrollbar and leaves only Textual's MessageLog scrollbar visible.
