# Investigate removing the design phase in favor of epics

Investigate whether Kingdom should remove the dedicated design phase entirely and instead let users model larger planning work as epics when they want more structure. This should revisit existing design-phase friction tickets and decide whether the workflow should be ticket/epic-first by default.

### 2026-08-03 — Audit complete: hide the phase, retain optional design

#### Product decision

**Recommendation: hide, not remove, deprecate, or keep as a first-class phase.**
Tickets and epics are the default planning model. A design document remains an
on-demand planning artifact and `kd design` remains callable for existing
repositories and power users, but it should be hidden from the default journey.
`design_approved` must not gate work. Existing `design.md` and `breakdown.md`
files remain readable in place.

This is the smallest migration-safe choice:

- removal would discard a still-useful advanced planning tool and create needless
  pressure to migrate tracked historical content;
- deprecation would promise eventual removal even though optional design remains
  useful;
- keeping the phase prominent preserves the current contradiction between a
  ticket-first runtime and design-first setup/help;
- hiding changes defaults and framing without breaking old repositories.

Council thread `council-bd26` supports this choice. Codex provided the substantive
recommendation above. Claude returned only an expired-OAuth `401`, so this is not
multi-model consensus; the epic owner authorized the product call with that
limitation recorded. The council response cited `src/kingdom/cli/init.py`, but the
actual file is `src/kingdom/cli/__init__.py`.

#### Epic-first replacement workflow

The default workflow should be:

1. `kd start` initializes or resumes branch/workspace runtime state without
   creating planning documents.
2. For one scoped outcome, create/pull a normal ticket and work it directly.
3. For a larger outcome, create `kd tk create --type epic "<outcome>"`, locate
   its Markdown with `kd tk find <epic-id>`, and put Goal, Context, Requirements,
   Non-Goals, Decisions, Open Questions, Acceptance Criteria, and durable Worklog
   entries in that one canonical artifact. These are the useful fields from the
   old design template without a separate phase or approval bit.
4. Consult council only at a real decision point, referencing the epic/ticket;
   record the decision in the epic Worklog.
5. Create executable children with
   `kd tk create --parent <epic-id> "<work item>"`; add dependency edges where
   order matters. Children and dependencies are the executable breakdown.
6. Execute children directly, with native subagents, reviewed peasants, or an
   optional `kd lord start <epic-id>` according to scope. Close each child, then
   close the epic after the built-in open-child guard passes; finish with
   `kd done`.

For a backlog sprint, the path is simply `kd start` → `kd tk pull <ids>` →
`kd tk start <id>` → Worklog/code/tests → `kd tk close <id>` → `kd done`.
Existing parent/dependency metadata comes with pulled tickets; no planning artifact
is synthesized.

Optional planning remains deliberate: an explicit `kd design` invocation should
initialize or reveal `design.md` on demand, and `kd design show` should continue
to render an existing file. Help and missing-file messages should say that design
is optional. `kd design approve` may remain callable/hidden for compatibility,
but approval has no workflow effect and should not be taught as a step.

#### Migration and backward compatibility

Repository evidence shows this is material tracked content, not hypothetical:

- `.kd/branches`: 21 `design.md` files (all non-empty) and 20 `breakdown.md`
  files (6 non-empty);
- `.kd/archive`: 7 `design.md` files (all non-empty) and 7 `breakdown.md` files
  (2 non-empty).

Migration rules:

- never delete, rename, rewrite, move, or auto-convert existing design/breakdown
  artifacts during `kd start`, `kd switch`, `kd done`, or `kd update`;
- stop scaffolding the files only for new branch layouts; generic branch/archive
  traversal already tolerates extra Markdown files, so old repositories remain
  readable without a schema migration;
- preserve old paths so council-thread references and Git history remain valid;
- leave any existing `design_approved` key untouched and treat it as inert legacy
  metadata; do not require it for starting tickets, status health, or completion;
- do not automatically copy a design into an epic. A design can contain historical
  rationale spanning already-created tickets, and archived designs should remain
  immutable. Users may manually copy still-current Goal/Context/Decisions into an
  epic and link the old path when that adds value;
- keep current `kd status --json` keys during the compatibility window unless a
  versioned schema break is chosen. Human help/status should be ticket/context-first
  and show design only when present. Older CLIs may recreate scaffolding if run on
  a new repository, but that is harmless and does not lose data.

No migration command is required. This is a default/scaffolding change with a
non-destructive legacy read path.
