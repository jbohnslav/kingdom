# Prevent development dogfooding with a stale installed kd binary

During `f122`, bare `kd tk current` continued running the installed release and
reported the branch-global ticket with `assignee: hand`, while
`uv run --project … kd` correctly exercised the working-tree implementation. This
is especially dangerous in a self-hosting project because commands succeed and
produce plausible but stale results.

## Acceptance Criteria

- [x] Development docs and the repo skill identify the canonical checkout invocation.
- [x] A developer gets a visible version/source mismatch warning when bare `kd` is stale, or setup makes the checkout command authoritative.
- [x] Tests cover the chosen version/source detection without depending on network access.
- [x] Dogfood and release instructions consistently exercise working-tree code.
- [x] Normal installed-user workflows remain quiet and unchanged.

## Worklog

### 2026-08-03 — Root cause and design

Bare `kd` can successfully run a separately installed `kingdom-cli` while the
current directory is this repository. Comparing only versions is insufficient:
development changes commonly leave `pyproject.toml` at the released version.
The robust signal is source provenance. When the command runs anywhere inside a
Kingdom checkout, its loaded `kingdom` module should resolve under that checkout's
`src/kingdom`; otherwise the CLI should warn and point to the canonical
`uv run kd` invocation. Outside a Kingdom checkout there is no expected source
tree, so normal installed-user commands remain quiet.

Planned regression coverage is filesystem-only: synthetic checkout markers and
explicit module paths, with no package index or network dependency. The warning
will be emitted from the top-level callback so it covers every subcommand.

### 2026-08-03 — Failing regression established

Added `tests/test_cli_development_source.py` covering a stale installed module
inside a checkout, working-tree execution, ordinary installed-user execution,
and callback emission. Before implementation,
`uv run pytest -q tests/test_cli_development_source.py` fails during collection
because `development_source_warning` does not exist. This confirms the test was
introduced before the fix.

### 2026-08-03 — Implemented and verified

Implemented a top-level source-provenance check in `src/kingdom/cli/__init__.py`.
Two local markers identify a Kingdom checkout (`pyproject.toml` and the canonical
CLI source file); the loaded module path is then compared with that checkout's
resolved `src/kingdom` directory. A mismatch prints one warning to stderr with
the `uv run kd` remediation. A working-tree module or any invocation outside a
Kingdom checkout returns without output. The check uses only `pathlib` and the
local filesystem.

Updated `CLAUDE.md` (the `AGENTS.md` symlink target), `README.md`,
`docs/publish-checklist.md`, and the repository Kingdom skill so checkout
dogfooding and pre-release validation consistently use `uv run kd` / `uv run`.
The post-release checklist explicitly retains bare `kd` because that step
intentionally validates the installed artifact.

Verification:

- `uv run pytest -q` — 2,084 passed, 38 skipped, 1 xfailed.
- `uv run ruff check .` — all checks passed.
- Manual simulated-installed-source `kd status` — warning appeared before normal

- Manual `uv run kd status` from this checkout — normal status output with no
