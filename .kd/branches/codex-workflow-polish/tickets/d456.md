# Rework kingdom SKILL.md so the core loop is top-of-mind

## The problem

The King reported a bug with clear details ("peasant watch doesn't show council activity") and the agent jumped straight into exploring the codebase instead of making a ticket. Had to be told "bro, make a ticket!" — even though "King reports a bug → create a ticket" was already in the skill (line 27). It just didn't register because it's one pattern among ~250 lines of workflows, examples, command syntax, and error recovery.

The skill is trying to be a behavioral guide and a reference manual at the same time, and the reference material is drowning out the reflexes.

## What should be top-of-mind

The King's vision for the core loop — these four things should be tippity-top-of-mind at all times, impossible to miss:

1. King says something → **make a ticket**
2. Ticket exists → **send it to a peasant**
3. While working → **update the worklog often**
4. State changes → **update the ticket**

Everything else supports these. An agent reading this skill should reach for `kd tk create` as instinctively as breathing.

## Ticket files are just markdown — use them

Agents can and should edit ticket files directly too — tick off acceptance criteria, add notes, whatever. `kd tk log` is one way to update a ticket, but opening the file and writing in it is equally valid. The ticket is a living document. The skill should encourage agents to keep tickets updated by any means, not gate everything through CLI commands.

## Acceptance Criteria

- [x] Agent first resolves its context and searches active/recent/related tickets before creating one.
- [x] A genuinely new request produces a small ticket immediately; an existing request updates the existing ticket.
- [x] Durable worklog and state updates remain the dominant behavior, not buried among reference material.
- [x] The execution ladder covers direct work, native subagents, peasant, lord, and council.
- [x] Peasant-to-council review remains the default; native subagents are preferred for bounded host-local delegation.
- [x] The owning session is responsible for merging subagent results into the durable ticket.

## Revised Direction (2026-08-02)

The old "create before exploration" wording produced a duplicate umbrella ticket
for the already-existing multi-Hand epic. Preserve the reflex to write things down,
but add a fast context/current/search step first. Also replace "ticket exists → send
it to a peasant" with a deliberate execution choice; peasants are valuable for
unattended work, not a mandatory hop for every task.

## Worklog

### 2026-08-03 — Skill audit and structure decision

The current skill leads with unconditional ticket creation, then repeats the
same ticket/worklog behavior across cue examples, two workflows, working-ticket
rules, a ticket-Markdown section, automatic updates, and workflow reflexes.
Detailed error recovery and merge-conflict instructions further separate the
opening reflex from daily execution choices. This explains how the rule can be
present yet fail to stay salient.

Decision: make the dominant path one short loop: resolve the owning context and
search related work; update an existing ticket or create a genuinely new small
one; choose direct/native-subagent/peasant/lord/council deliberately; merge all
durable results into the ticket; verify, update state, and close. Native
subagents will be the preferred bounded host-local delegation mechanism, while
peasants remain the unattended isolated-worktree path with council review by
default. Command examples, lifecycle detail, failure recovery, and merge
recovery will live in the existing references.

### 2026-08-03 — Canonical skill reworked and manually audited

Replaced the repeated behavioral/reference mix with a five-step core loop at the
top of `skills/kingdom/SKILL.md`: resolve/search, update-or-create, choose an
execution level, persist durable state, then verify/transition. The opening now
explicitly prevents duplicate umbrella tickets while still requiring genuinely
new work to receive a concrete ticket before broad exploration.

The execution ladder distinguishes direct work, native subagents, reviewed
peasants, lord, and council. Native subagents are the default for bounded
host-local delegation; the owning session retains responsibility for reviewing
and merging their findings, changes, evidence, and concerns into the ticket.

review by default. Council approval informs—but does not replace—the owning
session's integration review.
