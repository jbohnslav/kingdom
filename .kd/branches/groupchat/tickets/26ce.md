# Chat TUI crash: AttributeError style object has no attribute _color

## Severity

**P0 — Total blocker.** The TUI is completely unusable over SSH + tmux + iTerm2 integration. Crashes on the very first turn, every time. The King's primary development environment hits this on every launch, meaning `kd chat` is effectively broken.

## Environment

- SSH into a remote machine
- tmux with iTerm2's `-CC` integration mode
- Crash is immediate — not after extended use
- Also likely affects plain tmux sessions with misconfigured `$TERM`

## Root Cause Analysis

The crash has three contributing layers:

### 1. Textual defaults can fail in degraded terminal color environments

`ChatApp` calls `super().__init__()` with default settings (`src/kingdom/tui/app.py:353`). In Textual 7.5.0, that means `ansi_color=False` and color system auto-detection. If terminal color capability is corrupted/misreported, Textual/Rich style handling can produce the observed `AttributeError: style object has no attribute '_color'`.

### 2. iTerm2's tmux `-CC` integration corrupts color state

iTerm2's tmux integration mode (`tmux -CC`) has known issues:
- Color settings can be lost entirely after reconnect/reattach ([iTerm2 #4616](https://gitlab.com/gnachman/iterm2/-/issues/4616))
- Terminal rendering breaks after sleep/reconnect ([iTerm2 #9343](https://gitlab.com/gnachman/iterm2/-/issues/9343))
- Some tmux features aren't supported in integration mode at all ([iTerm2 tmux docs](https://iterm2.com/3.2/documentation-tmux-integration.html))

### 3. tmux + Textual require specific terminal config

Textual community reports show tmux compatibility depends heavily on `$TERM` and terminal-overrides:
- `tmux-256color` or `screen-256color` required for basic compat ([Textual #4003](https://github.com/Textualize/textual/discussions/4003))
- `xterm-256color` inside tmux causes rendering breakage ([Textual #5880](https://github.com/Textualize/textual/issues/5880))
- SSH + tmux + iTerm2 combo specifically reported as broken ([Textual #1517](https://github.com/Textualize/textual/issues/1517))

### Crash path

SSH → tmux `-CC` → iTerm2 integration → color capabilities misreported or lost → Textual auto-detects wrong color system → `Style` objects partially initialized → `_color` attribute missing → `AttributeError` on first render.

## Code Audit: Where It Breaks

No SSH/tmux/terminal detection exists in the TUI code. The entire app runs identically regardless of terminal environment.

Vulnerable style assignment sites (no error handling):
- `src/kingdom/tui/widgets.py:218` — `MessagePanel.compose()`: `self.styles.border = ("round", color)`
- `src/kingdom/tui/widgets.py:275` — `StreamingPanel.compose()`: `self.styles.border = ("round", color)`
- `src/kingdom/tui/widgets.py:315` — `WaitingPanel.compose()`: `self.styles.border = ("dashed", color)`
- `src/kingdom/tui/widgets.py:401` — `ThinkingPanel.compose()`: `self.styles.border = ("dashed", color)`
- `src/kingdom/tui/widgets.py:370-376` — `ErrorPanel.compose()`: hardcoded color strings

Only `ColoredMentionMarkdown` (line 165-168) has a try/except around style operations.

Color values come from `color_for_member()` which returns valid strings (`"#d97706"`, `"magenta"`, etc.), so the colors themselves aren't the problem — it's Textual's internal rendering pipeline choking when color capabilities are degraded.

## Fix Strategy

### Phase 1: Immediate — proactive `tmux -CC` mitigation + crash fallback

1. **Detect tmux control mode for the current session**, not just "SSH + tmux":
   - Resolve current tmux session: `tmux display-message -p '#{session_name}'`
   - Query clients on that session only: `tmux list-clients -t <session> -F '#{client_control_mode}'`
   - If any client reports `1`, we are in control mode (`tmux -CC`) and should enable compatibility mode.

2. **In detected control mode, start TUI with `ansi_color=True`**:
   - Set at app init (`super().__init__(ansi_color=True)`) or equivalent runtime toggle.
   - This avoids forced truecolor conversion while preserving a usable themed UI.
   - Do not blanket-downgrade all SSH/tmux users.

3. **Add one-time boundary fallback around `app.run()`**:
   - If startup/render still throws `AttributeError` with `_color`, relaunch once in stricter safe mode (`TEXTUAL_COLOR_SYSTEM=eight_bit`).
   - Print one clear warning with override guidance and avoid repeated crash loops.

4. **Add explicit override flag/env for color mode**:
   - Example: `kd chat --color auto|truecolor|eight-bit|standard|none`
   - Default remains `auto`.

### Phase 2: Resilience and observability

5. **Avoid broad try/except around every style assignment**:
   - Catching style errors at widget sites risks masking unrelated bugs.
   - Keep fallback at TUI boundary and log exact failure context for triage.

6. **Optional plain fallback mode**:
   - `--no-tui` can be tracked as follow-up if needed, but is not required to ship the P0 unblock.

### Phase 3: Documentation

7. **Document terminal compatibility** in README or `kd chat --help`:
   - Recommended tmux config: `default-terminal tmux-256color` (or `screen-256color` when needed)
   - Known high-risk mode: iTerm2 tmux `-CC` integration
   - Workarounds: `--color ...`, `NO_COLOR=1`

## Post-Implementation Review

Initial implementation landed. Core detection and fallback work correctly — full test suite passes (1396 passed). The following issues were identified during review and need to be addressed before closing.

### Issue 1 (High): `--color` validation happens after side effects

**Found by:** Codex
**Agreed by:** Claude

`--color` is validated at `cli.py:1607` but the `--new` branch at `cli.py:1558` runs first, calling `create_thread(...)`. So `kd chat --new --color bogus` creates an orphaned thread before erroring out.

**Fix:** Use `click.Choice` on the typer param (`typer.Option(..., click_type=click.Choice(["auto", "truecolor", "ansi", "none"]))`) so invalid values are rejected by the framework before the function body runs. This also gives `--help` docs and tab completion for free. Alternatively, move validation above the `--new` branch.

### Issue 2 (Medium): `--color none` doesn't actually disable colors

**Found by:** Codex
**Agreed by:** Claude

Current `none` path sets `NO_COLOR=1` in the environment and `use_ansi=False`, but `ChatApp` only forwards `ansi_color` to Textual's `super().__init__()`. It never passes `NO_COLOR` through to the Textual `App` constructor, so the app console still reports `no_color=False` and `color_system=truecolor` at runtime.

**Fix:** Either pass `NO_COLOR` through so Textual actually respects it (set env var before `App.run()` is called, or find the Textual constructor param), or change the help text to an accurate, weaker promise ("best-effort hint to disable colors"). Could also be a follow-up ticket if it doesn't block the P0 use case.

### Issue 3 (Low): Subdirectory test doesn't actually test from subdirectory

**Found by:** Codex
**Note:** This is from ef8e changes mixed into the same diff, not 26ce proper.

`test_peasant_command_from_subdirectory` at `test_cli_peasant.py:1773` creates `subdir` but never changes cwd or patches `Path.cwd()`, so it doesn't prove the stated behavior.

**Fix:** Patch `Path.cwd()` to return the subdirectory path, or use `monkeypatch.chdir()`. Address under ef8e, not here.

### Additional Suggestions

- **`typer.echo()` message placement (Claude):** The "Detected tmux control mode..." message prints before the TUI launches. In `-CC` mode it may flash and disappear when the TUI takes over the screen. Consider logging it or showing it as an in-TUI notification instead. Non-blocking.

- **Crash fallback vs `--color none` conflict (Claude):** If a user explicitly passes `--color none` and the `_color` crash still fires, the fallback retries with `ansi_color=True`, overriding the user's explicit choice. The fallback should probably respect explicit `--color` and not retry if the user made a deliberate choice.

- **Separate commits (Claude):** The ef8e changes (`require_project_root()` in `resolve_peasant_context`, `cycles.append` fix) are mixed into the 26ce diff. These should be in their own commit under ef8e.
