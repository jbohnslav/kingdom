# Add `kd tk bless` — council-assisted ticket vetting

Add `kd tk bless <id>` command that sends a ticket to the council for structured pre-handoff review. The council evaluates whether the ticket is ready for a peasant to execute — this is the "seek the council's blessing" step before dispatching work.

**Lifecycle:** `create → bless → peasant start → review (completed work)`

- `bless` = council checks a plan *before* execution (input vetting)
- `review` = council checks code *after* execution (output review)

The council prompt should ask members to evaluate:
- Ambiguity in description or AC
- Missing or weak acceptance criteria
- Scope (too big for one ticket? needs breakdown?)
- Missing dependencies
- Whether a peasant could execute it without guessing
- Priority/type correctness

Council responses should be structured and actionable, not free-form essays. No auto-apply — the hand or King arbitrates.

## Future: `kd tk draft`
A separate follow-up (`kd tk draft "idea"`) could let council create a ticket from scratch. Out of scope here — `bless` is review-only for existing tickets.

## Acceptance Criteria

- [ ] `kd tk bless <id>` sends the ticket to council for structured pre-handoff review
- [ ] Council prompt explicitly checks for ambiguity, missing AC, scope, deps, and peasant-readiness
- [ ] Council responses are structured (not free-form) — suggestions map to ticket fields
- [ ] No auto-apply: review output is informational, hand/King decides what to change
- [ ] Reuses council selection/async flags (--to, --async, --no-watch) where applicable
- [ ] Command errors clearly if ticket ID doesn't exist or ticket is already closed
