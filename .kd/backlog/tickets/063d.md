# Refresh context activity on owner ticket commands

## Acceptance Criteria

- [ ] A ticket command run by the ticket's exact owning context refreshes that
  context's `last_seen` timestamp when the command demonstrates activity.
- [ ] At minimum, `kd tk log` refreshes activity; decide and document whether
  other owner-scoped mutations should do the same.
- [ ] Commands run by a different context for that ticket do not keep the owner
  artificially live.
- [ ] `kd status` does not mark a diligently logging long-running owner stale
  merely because it has not rerun `kd tk current` or `kd tk start`.
- [ ] Focused tests cover exact-owner activity, foreign-context logging, and the
  stale threshold.

## Context

Ticket `b507` dogfooding used three real contexts on one branch. After this
context ran several `kd tk log b507` commands, `kd status --stale-hours 0.01`
still marked it stale because `ticket_log` resolves the context only to label the
author and never persists its new `last_seen`. Running `kd tk current --id`
immediately made only this owner live again. The output is internally consistent,
but it makes a session following the documented durable-log loop look inactive;
with the default 24-hour threshold the same false stale classification affects
long-lived sessions.

Do not refresh activity from arbitrary reads or another worker's log against the
same ticket. The update must preserve exact context ownership semantics.
